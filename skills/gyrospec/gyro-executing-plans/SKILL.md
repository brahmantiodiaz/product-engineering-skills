# Executing plans

1. Call the Skill tool with "gyro". Follow its Node 20+ check, script path, language, and format rules. Reply in the user's language and keep convention keywords English. This workflow adapts Superpowers executing-plans; attribution is in the plugin repository's `THIRD_PARTY_NOTICES.md`.
2. Require `<slug> <nn>`, normalize `nn`, and run `gyro status <slug> --json` before work. Locate the reviewed `docs/superpowers/plans/<YYYY-MM-DD>-<slug>-<nn>.md`; if several match, ask which plan to execute. Verify its `Ticket`, `Sub-ticket`, and `Spec revision` header. The named ticket must exist and not be stale; the plan revision must equal the current approved spec revision, upstream gates must be current, and `gyro check <slug> tickets` is clean (show its lines and suggest `/gyro-breakdown <slug>` otherwise). Check blocking dependencies are done. If a prerequisite fails, name the missing plan, gate, revision, dependency, or stale cause, suggest `/gyro-writing-plans <slug> <nn>`, `/gyro-breakdown <slug>`, or the reported `next` as appropriate, and stop. Do not resume a done ticket without a human request to reopen it.
3. Read the entire plan, sub-ticket, approved spec snapshot, referenced PRD blocks, and repository instructions before execution. Critically review paths, interfaces, assumptions, and commands. If the plan cannot work as written, explain the concrete issue and proposed smallest deviation to the user. Do not silently redesign approved behavior. A step requiring a human is a blocker: run `gyro ticket <slug> <nn> --status blocked --reason "<why>"`, report it, and stop until resolved.
4. Fix the review baseline once per plan, so a later session reviews exactly this plan's work:
   - If the plan file already has a `**Execution start:** <sha>` line, this is a resume: reuse that commit and do not record a new one. Then run `git status --porcelain` and `git diff <start>`, and show the user every change that the plan's completed tasks do not account for, especially anything that appeared since the last session. Ask which of those belong to this plan. Record the rest under `**Out of scope:**` below the `Execution start` line (file paths, or file plus hunk description), leave them untouched, and keep them out of scope for review and fixes.
   - Otherwise run `git status --porcelain`. When it shows changes, they are someone else's WIP: ask the user to commit or set them aside before execution starts, and do not proceed while they are mixed into the tree. Never stash or discard them yourself.
   - With a clean tree, add `**Execution start:** <output of git rev-parse HEAD>` under the plan's header and keep it there for the rest of the plan.

   Then run `gyro ticket <slug> <nn> --status in_progress`. Invocation authorizes executing this plan within the user's stated scope; it does not grant new commit, publication, deployment, or PR permissions.
5. Call the Skill tool with "tdd". Work tasks in the plan's order: write the failing test, run it and verify the expected failure, implement, and rerun to the expected pass. Execute every verification command and compare its output with the plan's expectation. Mark completed task checkboxes in the implementation plan only after their proof passes. Do not skip failing checks or label unrun checks as passing. Report any mismatch, diagnose it, and resolve it within scope. When a human decision, credential, external action, or impossible requirement prevents progress, set `blocked --reason "<why>"` and stop with the evidence.
6. Recheck every prerequisite from step 2 with `gyro status <slug> --json` after any interruption and again immediately before marking the ticket done: the PRD, prototype, and spec gates are current (a gate shows `draft` when its file was edited without re-approval, even though its revision did not change), the ticket is not stale, every `blocked_by` ticket is done, and the plan's `Spec revision` equals the current approved spec revision. If any fails, run `gyro ticket <slug> <nn> --status blocked --reason "<which prerequisite failed>"`, name the phase that fixes it (`/gyro-prd`, `/gyro-prototype`, `/gyro-spec`, `/gyro-breakdown`, or `/gyro-writing-plans`), and stop; never mark the ticket done past a failed check. Do not edit `gates.json`, snapshots, or `spec_revision` to bypass staleness. If this prevents execution, record the blocking reason.
7. After the last task and all verification pass, Call the Skill tool with "code-review". Give it everything it would otherwise look for elsewhere:
   - the fixed point: the `**Execution start:**` commit from the plan file;
   - the spec source: the approved spec snapshot `.gyro/<slug>/approved/spec.<n>.md`, the sub-ticket file, and the plan; local mode has no issue tracker, so tell it not to look for one or ask for `/setup-matt-pocock-skills`;
   - the changes: `code-review` diffs committed work only (`git diff <start>...HEAD`). When this plan's work is not all committed, also give it `git diff <start>` (every committed, staged, and unstaged change since the execution start) and the contents of every new untracked file, and tell it that this working-tree diff is the review input: an empty committed diff is expected here, so it must skip its non-empty check on `git diff <start>...HEAD` and give both review axes the same working-tree scope. Because step 4 started from a clean tree, all of it is this plan's work, including edits to files that were touched before, except what the plan lists under `**Out of scope:**`; pass that list so neither axis reviews it and no fix touches it.

   Address its Critical and Important findings with a failing test first, then the fix and relevant verification. Repeat review of the corrections as needed until those findings are resolved. Do not claim verification proves a live deployment or human acceptance that was not performed.
8. Ask the user for the PR URL, or create the PR only if they ask and the necessary publication actions are authorized. If the PR URL or publication is awaiting a human, run `gyro ticket <slug> <nn> --status blocked --reason "Awaiting PR URL after verification"` and stop; do not invent a URL or mark the ticket done. Once a real `http://` or `https://` PR URL is provided and verification is complete, run `gyro ticket <slug> <nn> --status done --pr <url>`.
9. Run `gyro status <slug> --json` and `gyro status <slug>`. Report the finished work and proof, then tell the user the next step is the returned `next`, which may be `/gyro-writing-plans <slug> <next nn>` or `All sub-tickets are done.` Stop. Never invoke another phase automatically.
